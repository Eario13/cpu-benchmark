# Сравнение SFBench на пяти ОС

Дата испытаний: 16 августа 2026 года.

## Стенд и методика

- Supermicro PIO-628U-TR4T+-ST031, BIOS 3.2a.
- 2 × Intel Xeon E5-2667 v4, всего 16 физических ядер / 32 потока, 2 NUMA-узла.
- На каждой ОС выполнено по три запуска в исходном режиме питания и по три в максимальном режиме.
- Каждый JSON содержит 3 секунды прогрева, 10 секунд Single и 10 секунд Multi.
- Windows: один и тот же бинарник MSVC. Максимальный режим — `High performance`; процесс запускается с высоким приоритетом.
- Windows Server: текущий код SFBench дополнительно сам временно включает `High performance`, HighQoS, высокий приоритет и калибрует ядро для Single. После теста исходная схема восстанавливается. Поэтому строка `default` на Server показывает исходную схему с автоматической временной настройкой внутри SFBench.
- Ubuntu: ядро `7.0.0-29-generic`, GCC 15.2, профиль `-O3 -march=native -mtune=native`, IPO/LTO. Сравнивались governor `schedutil` и `performance`; исходный `schedutil` восстановлен.
- На Windows отсутствуют драйверы ряда Intel chipset/uncore-устройств. Список практически одинаков: 161 проблемное PCI-устройство на Windows 10/11 и 162 на обеих Windows Server.

### Повтор Ubuntu после исправления GCC hot loop

| Вариант | Single | Multi |
|---|---:|---:|
| До исправления, `performance` | 1145 / 1146 / 1146 (**1145,67**) | 19846 / 19844 / 19844 (**19844,67**) |
| Исправленный регистровый loop | 1146 / 1146 / 1146 (**1146,00**) | 22322 / 22323 / 22323 (**22322,67**) |

Контрольный A/B исходного бинарника дал MT 19836,33 с affinity и 19838,33 без
affinity. Разница менее 0,02%, поэтому NUMA/affinity не являлись причиной потери.
Дизассемблирование показало реальную причину: GCC загружал константы внутри каждой
итерации, тогда как MSVC держал их в регистрах и разворачивал цикл. После явного
восьмикратного разворачивания и фиксации констант в регистрах математическая нагрузка
осталась прежней, а Linux MT вырос примерно на 12,49% относительно первоначальной
серии.

Удалённая проверка выполнялась кандидатом
`beta 0.47-native-x86-64-v3-mtfix1`. Тот же исправленный цикл перенесён в
основную ветку как `beta 0.48`. Smoke-test финальной native-сборки дал Single
1146 и Multi 22314.

Дополнительный контрольный запуск уже собранного Linux-бинарника `beta 0.48`
при восстановленном governor `schedutil` дал Single 1145 и Multi 22255. Это на
0,30% ниже среднего прогона `performance` и укладывается в нормальное влияние
режима питания и межзапусковой разброс.

## Частота и режим питания

| ОС / режим | Наблюдение |
|---|---|
| Ubuntu `schedutil` | Средняя Busy MHz по трём полным прогонам: 3471 / 3473 / 3470 |
| Ubuntu `performance` | Средняя Busy MHz: 3501 / 3502 / 3502; эффект на score всего +0,03% Single и +0,10% Multi |
| Ubuntu, исправленный loop | Busy MHz: 3503 / 3503 / 3503; MT вырос без существенного изменения частоты |
| Windows 10 `High performance` | Максимальная расчётная WMI-частота: 3553 МГц |
| Windows 11 `High performance` | Максимальная расчётная WMI-частота: 3585 МГц |
| Windows Server 2022 `High performance` | Максимальная расчётная WMI-частота: 3553 МГц |
| Windows Server 2025 `High performance` | Максимальная расчётная WMI-частота: 3521 МГц |

WMI `_Total` усредняет все логические процессоры и не является точной частотой выбранного Single-ядра. Поэтому её можно использовать как подтверждающий индикатор, но не как самостоятельное объяснение результата.

## Выводы

1. После исправления Ubuntu и Windows дают практически одинаковый результат: Single отличается не более чем на 0,12% для Ubuntu/Windows 10/11/Server 2022, а Multi — не более чем на 0,17% относительно Windows 10.
2. Причина прежнего отставания Ubuntu Multi на 11,25% была найдена в машинном коде GCC, а не в Linux scheduler, NUMA или частоте. Affinity A/B менял Multi менее чем на 0,02%, Busy MHz после исправления осталась около 3503 МГц, но Multi вырос на 12,49%.
3. Исправление сохраняет прежнюю математическую нагрузку: восемь независимых цепочек, восемь FMA на логическую итерацию и 16 учитываемых FLOP. Меняется только размещение констант и явное восьмикратное разворачивание внешнего цикла.
4. Windows-производительность должна остаться прежней: MSVC уже держал константы в регистрах и разворачивал цикл аналогично. Это подтверждено сравнением машинного кода; полный повторный прогон Windows `beta 0.48` пока не выполнялся.
5. Двукратная разница Single на этом стенде **не воспроизводится**. Windows 10, Windows 11, Windows Server 2022 и Ubuntu дают 1144–1146. Значит, исходная аномалия другого сервера требует отдельной проверки BIOS, выбранного ядра, turbo, плана питания и фоновой нагрузки.
6. Автоматическая настройка Windows Server работает: временно включаются `High performance`, HighQoS, высокий приоритет и калибровка ST-ядра, затем исходный план восстанавливается. Server 2022 равен Windows 10/11.
7. На Server 2025 сохраняется отдельное снижение Single на 3,49% при одинаковом Multi. Наблюдаемая WMI-частота объясняет только часть разницы; точную причину без отдельного A/B-теста политик защиты, служб и планировщика определить нельзя.
8. Отсутствующие драйверы не объясняют разницу между протестированными Windows: набор проблемных Intel PCI-устройств почти одинаков. Для окончательного сертификационного замера драйверы чипсета всё же следует установить одинаково на все ОС.
